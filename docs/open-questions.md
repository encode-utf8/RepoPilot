# 未决问题与设计补充

本文记录 `RepoPilot.md` 未定义、或需要后续阶段确认的设计点，以及阶段一为推进实现所作出的**临时决定**。
每一项都标注了当前处理方式与影响，便于后续阶段重新评估。若与 `RepoPilot.md` 冲突，以设计文档为准。

## 1. 任务持久化

- **问题**：设计文档规定任务状态保存在数据库（阶段四 PostgreSQL），阶段一未引入数据库。
- **当前处理**：`InMemoryTaskStore`（进程内、带锁、深拷贝隔离）。任务与报告随进程退出而丢失。
- **影响**：重启后无法查询历史任务；多进程部署（多 worker）无法共享状态，因此阶段一必须以单进程运行。
- **建议**：阶段四实现 `TaskStore` 协议的 PostgreSQL 版本，并把报告 JSON 一并持久化。

## 2. 任务调度

- **问题**：设计文档要求「长时间运行的任务通过异步队列调度」，阶段一未引入 Redis。
- **当前处理**：`ThreadPoolTaskScheduler`（线程池 + 协作式取消令牌），API 立即返回 `task_id`。
- **影响**：任务并发受 `REPOPILOT_SCHEDULER_MAX_WORKERS` 限制；无跨进程排队、无重试与优先级。
- **建议**：阶段四实现基于 Redis 的 `TaskScheduler`，保持协议不变。

## 3. 沙箱隔离强度

- **问题**：设计文档要求「不可信代码在隔离环境内执行」（Docker），阶段一未引入容器。
- **当前处理**：`LocalProcessSandboxExecutor` —— 环境变量白名单、凭据剥离、超时、输出上限、进程树终止、`HOME`/`TEMP` 重定向、默认禁止执行非受信仓库代码。这是**加固的本地进程执行**，不是容器隔离。
- **影响**：对已开启执行的仓库，恶意代码仍可访问工作区之外的宿主文件系统与网络；无内存/CPU/磁盘配额。
- **建议**：阶段二引入 Docker（只读挂载工作区、`--network=none`、资源上限、非 root 用户），并复用 `SandboxExecutor` 协议。

## 4. 检查器使用的 Python 环境

- **问题**：设计文档未规定运行仓库测试时使用哪个解释器/虚拟环境。
- **当前处理**：使用宿主解释器（`Settings.python_executable`，默认当前进程的 `sys.executable`），只把仓库目录作为工作目录。受控 fixture 仅依赖标准库，因此可复现。
- **影响**：真实第三方仓库的测试大概率因缺少依赖而失败或产生假阴性；未创建按仓库的虚拟环境。
- **建议**：阶段二为每个任务构建独立虚拟环境（`python -m venv` + 安装依赖，或复用锁文件），并在报告中记录环境指纹。

## 5. 依赖告警的严重程度

- **问题**：pip-audit 默认查询的 PyPI 服务不返回 CVSS/严重度；设计文档要求每条问题包含「严重程度」。
- **当前处理**：统一标为 `high`，并在 `metadata.severity_source` 中注明「advisory 未提供 CVSS」。
- **影响**：严重程度不反映真实风险，可能高估低危告警。
- **建议**：改用 OSV 服务（`--vulnerability-service osv`）并解析 CVSS/生态字段，或引入人工分级表。

## 6. 报告 schema 稳定性

- **问题**：设计文档未定义报告字段的演进策略。
- **当前处理**：报告含 `schema_version: "1.0"`；字段一次性定义于 `src/repopilot/models.py`，未知字段被 Pydantic 拒绝。
- **影响**：后续增删字段需要显式升级版本号并同步消费方（Dify、Agent）。
- **建议**：把报告当作对外契约，变更时递增 `schema_version` 并在本文登记。

## 7. `needs_review` 是否为独立状态

- **问题**：设计文档只提到「标记为失败或需要人工审核」，未定义状态枚举。
- **当前处理**：独立状态 `needs_review`，与 `failed` 区分：`failed` 表示执行出错，`needs_review` 表示执行完成但结论不完整（有必需检查器未运行）。
- **影响**：消费方需同时处理 `failed` 与 `needs_review` 才能判断「未成功」。
- **建议**：阶段二如需简化，可退回 `failed` + `verification.fully_verified=false` 标记；反之应在设计文档中固化 `needs_review`。

## 8. 检查器严格性的策略入口

- **问题**：设计文档未规定「检查器无法运行时」的默认行为。
- **当前处理**：`REPOPILOT_REQUIRE_PYTEST_FOR_DETECTED_TESTS=true`（检测到测试却未执行 → `needs_review`）；`REPOPILOT_REQUIRE_DEPENDENCY_AUDIT=false`（依赖审计不可用只作为限制记录，不阻断）。
- **影响**：默认对测试执行严格、对依赖审计宽松。
- **建议**：阶段二把两者纳入任务级参数（用户可在创建任务时声明严格程度）。

## 9. 依赖清单覆盖范围

- **问题**：不同项目使用 requirements.txt / pyproject / Poetry / PDM / uv lock / Pipenv。
- **当前处理**：审计所有 `requirements*.txt`；若无则从 `pyproject.toml` 的 `[project] dependencies` 与 optional-dependencies 生成临时 requirements 文件。锁文件（`poetry.lock`、`pdm.lock`、`uv.lock`）已检测但未使用。
- **影响**：只声明锁文件的项目依赖审计会退化为「不适用」。
- **建议**：阶段二支持 `pip-audit --locked` 与各包管理器的锁文件解析。

## 10. 受信任来源的登记方式

- **问题**：设计文档要求「默认关闭对第三方仓库的代码执行」，但未定义如何标记可信来源。
- **当前处理**：目录白名单 `REPOPILOT_TRUSTED_SOURCE_ROOTS`（仅本地路径，且需严格包含于白名单目录之下）；`file://` 视为本地路径；其余一律不可信。
- **影响**：只能通过部署配置放行，无法按任务粒度授权；白名单内的任何仓库都可执行代码。
- **建议**：阶段四引入凭据管理层后，改为「按仓库 + 按操作」的显式授权记录。

## 11. 仓库自带配置的可信度

- **问题**：Ruff / pytest 会读取仓库内配置，配置本身可能影响执行（如 `--cov` 插件、`extend` 路径）。
- **当前处理**：pytest 使用 `-o addopts=` 清空仓库的 `addopts`、`-p no:cacheprovider`、显式 `--rootdir`；Ruff 保留仓库配置（含 `select`/`ignore`），但不读取仓库外路径。
- **影响**：清空 `addopts` 可能改变项目预期的测试命令（例如缺少覆盖率门禁）；Ruff 配置来自仓库，其结果不完全由我们控制。
- **建议**：阶段二明确「以仓库声明的测试命令为准」并记录实际命令；对 Ruff 配置做快照存入报告。

## 12. 私有仓库与网络策略

- **问题**：设计文档要求凭据不进入模型上下文与沙箱，但未定义私有仓库的拉取方式。
- **当前处理**：不向子进程传入任何凭据（`GIT_TERMINAL_PROMPT=0`、空 `GIT_CONFIG_GLOBAL`），私有仓库一律克隆失败并落 `failed`。
- **影响**：阶段一只能评估公开仓库与本地 fixture。
- **建议**：阶段三引入后端的凭据管理层，通过受控的 git 凭据助手或 GitHub App 安装令牌注入，且仍然不进入模型上下文。

## 13. 取消语义

- **问题**：设计文档只要求「取消尚可终止的任务」，未定义实现语义。
- **当前处理**：协作式取消令牌——命令执行期间每 50ms 轮询令牌并终止进程树；取消优先于其他判定，任务落 `cancelled`。
- **影响**：已完成的步骤不会回滚；若取消到达时任务刚好结束，结果仍可能是 `succeeded`（接口会返回 409）。
- **建议**：阶段四引入队列后定义取消的持久化语义（含「取消中」中间状态）。

## 14. 资源限制

- **问题**：设计文档要求「容器资源限制」「模型调用预算」等成本控制。
- **当前处理**：仅实现时间上限与输出字节上限，另有 `max_scanned_files`、`max_evidence_chars` 限制扫描与证据体量。
- **影响**：无内存/CPU/磁盘/进程数上限，恶意或异常仓库可能耗尽宿主资源。
- **建议**：在 Docker 沙箱中通过 cgroup 施加限制，并增加单任务磁盘配额与清理策略。

## 15. 工作区与日志保留

- **问题**：设计文档未定义执行产物保留期。
- **当前处理**：默认保留工作区（`REPOPILOT_KEEP_WORKSPACE=true`），日志与报告副本写在 `REPOPILOT_LOG_DIR`；未实现清理任务。
- **影响**：长期运行会持续占用磁盘（克隆 + 报告 + JSONL）。
- **建议**：阶段四增加保留策略与后台清理，报告是否保留单独配置。

## 16. 重复提交的去重键

- **问题**：设计文档要求「重复提交同一任务时具有明确的去重策略」，未定义「同一任务」的判定。
- **当前处理**：`(repo_url 去尾斜杠, base_branch, base_commit)` 三元组；仅在存在**未终态**同键任务时返回既有 `task_id`（`deduplicated: true`）。
- **影响**：同一仓库不同分支会被视为不同任务；已终态任务允许重新提交（不返回缓存结果）。
- **建议**：如需结果缓存，应新增显式的「按 commit 复用报告」策略，并与去重区分开。

## 17. 通知/异步回调

- **问题**：设计文档提到「任务完成后通过接口返回报告和 PR 链接」，阶段一无推送机制。
- **当前处理**：仅提供轮询接口（`GET /api/tasks/{id}`）。
- **影响**：调用方需要轮询；无 webhook/事件流。
- **建议**：阶段四接入 Dify 时提供回调或 SSE 事件流。

## 18. 跨平台差异

- **问题**：设计文档未定义目标运行平台。
- **当前处理**：同时兼容 Windows 与 POSIX——Windows 用 `CREATE_NEW_PROCESS_GROUP` + `taskkill /F /T`，POSIX 用 `start_new_session` + 进程组 `SIGKILL`；路径在报告中统一为仓库相对 POSIX 形式；fixture 生成时固定 `core.autocrlf=false`。
- **影响**：Windows 下 git 的 `symbolic-ref` 探测默认分支依赖远端 `origin/HEAD`，缺失时回退到 `HEAD`；报告中的行号/列号来自工具输出，未做跨平台归一化测试。
- **建议**：明确 CI 平台矩阵（至少 Linux），并在 CI 中运行完整测试。

## 19. 启发式检查器的定位

- **问题**：设计文档中「未验证的潜在问题」来源是 LLM 分析（阶段二），阶段一没有 LLM。
- **当前处理**：由一个确定性的启发式检查器产出 `unverified_issues`（未固定版本依赖、被跳过的测试、静默吞异常、缺少测试），`origin` 仍为 `tool`、`verification=unverified`。
- **影响**：覆盖范围有限，且与阶段二的模型输出共用同一套 schema。
- **建议**：阶段二让模型输出复用 `Issue` 结构并置 `origin=model`、`verification=unverified`，本检查器保留为确定性兜底。
