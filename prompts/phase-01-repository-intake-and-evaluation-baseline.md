## 1. 背景

RepoPilot 是一个面向 GitHub 仓库的智能代码维护系统：用户提供仓库地址、Issue、CI 失败记录或仓库评估任务，系统自动完成仓库分析、问题定位、代码修改、测试验证与修复报告生成，并在满足质量门禁后创建 Draft PR（不自动合并）。整体流程：

```
用户提交任务 → FastAPI 创建任务 → 获取仓库并固定基线版本 → 执行仓库检查或 Agent 修复
→ 沙箱运行测试 → 质量门禁 → 创建 Draft PR → 保存执行记录并返回结果
```

实施顺序原则：**先完成仓库检查，再实现 Agent 修复；先跑通本地验证，再接入 GitHub 写操作。**

本次要完成的正是这条链路的**第一段（确定性部分）**：不依赖任何模型能力，就能稳定地把一个仓库拉下来、检查一遍、输出结构化评估报告。

## 5. 接口契约（设计文档 §3.1）

后端统一提供以下接口，本迭代全部实现：

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/tasks` | 创建仓库评估任务 |
| `GET` | `/api/tasks/{task_id}` | 查询任务状态 |
| `GET` | `/api/tasks/{task_id}/report` | 获取评估报告 |
| `GET` | `/api/tasks/{task_id}/logs` | 获取执行日志 |
| `POST` | `/api/tasks/{task_id}/cancel` | 取消尚可终止的任务 |

约定：

- `POST /api/tasks` 必须**立即返回** `task_id`，不得在请求内同步跑完整个克隆与检查流程（对应设计文档：「长时间运行的任务通过异步队列调度，API 请求不直接承担完整的代码执行过程」）。
- 任务状态建议枚举：`queued` / `running` / `succeeded` / `failed` / `cancelled`。报告未生成时 `GET /report` 返回明确错误码（如 `409`）而非空对象。
- 请求体至少包含：`repo_url`、`task_type`（本迭代仅 `repository_assessment`）、`base_branch`、可选 `base_commit`。额外字段按需扩展，并对未知字段保持明确行为。
- 每个任务必须**固定仓库地址、目标分支和基线 commit**（见 §7.2）。
- 错误响应统一为结构化 JSON（含 `error_code`、`message`），不要裸奔 `500`。

## 6. 数据契约

### 6.1 任务记录

至少记录：`task_id`、`run_id`、`repo_url`、`base_branch`、`resolved_commit`、`task_type`、`status`、`created_at` / `started_at` / `finished_at`、`failure_reason`、`duration`、资源消耗占位字段。

### 6.2 问题记录（评估报告核心结构）

设计文档 §3.2 明确：每条问题记录包括**问题类型、严重程度、文件路径、行号、问题证据、来源工具、修复建议**。请把这几项作为结构化字段落库，并额外保留 `origin` 字段区分来源：

- `origin = "tool"`：工具直接检测到的问题（静态检查错误、测试失败、已知依赖漏洞）。
- `origin = "model"`：模型分析得到的潜在问题，需进一步验证后才能确认。

本迭代只产出 `origin = "tool"`。**系统不得把模型提出的建议直接当作已确认缺陷**，该约束请在数据结构与文档中保留。

### 6.3 报告结构

报告至少包含：仓库元数据（识别到的语言、Python 版本、依赖清单、测试框架、常用开发工具）、各检查器的执行结果与原始输出摘要、问题列表、按严重程度/来源工具统计的汇总，以及检查过程中无法完成的事项（如测试无法运行、基线本身失败）。

### 6.4 日志格式

统一使用 `task_id` 与 `run_id` 关联的结构化日志（JSON Lines），字段至少包含时间戳、级别、事件名、任务/运行标识、结构化 payload。执行记录从项目初期就要建好，不要等到接入训练时再补。

## 7. 工程约束与技术约定

### 7.1 语言与依赖

- Python 3.11+，使用 `pyproject.toml` 管理依赖与工具配置。
- 本迭代允许的运行时依赖应保持精简：`fastapi`、`uvicorn`、`pydantic`、`pydantic-settings`、以及依赖风险扫描工具（优先 `pip-audit`，并说明选择理由）。测试依赖：`pytest`、`httpx`；开发依赖：`ruff`。
- **不要**在阶段一引入 `langgraph`、`vllm`、`pymilvus`、`dify-client` 等后续阶段依赖。

### 7.2 基线固定

克隆后必须把任务绑定到一个**确定的 commit**：若用户给了 `base_commit` 就用它，否则解析 `base_branch` 的当前 HEAD，并把解析结果写回任务记录。目的是「避免任务执行期间远端代码变化影响结果复现」。

### 7.3 执行与安全（设计文档 §5.2 安全性，硬性要求）

- 所有外部命令通过参数列表调用，**禁止 `shell=True` / 字符串拼接命令**。
- 所有子进程必须有**超时**与**输出大小上限**，超限需截断并记录。
- 不可信代码必须在隔离环境中执行。本迭代至少要做到：在独立临时工作目录内执行、不透传宿主环境变量（尤其凭据）、限制超时与输出；并把这套隔离封装在**唯一一个执行入口**后面（见 §7.4），为阶段二/三替换为 Docker 沙箱留好位置。
- 是否在本迭代引入 Docker 沙箱，请给出判断与理由；若引入，需保证在无 Docker 的机器上仍能跑通「受控 fixture」路径。
- 凭据绝不进入日志、报告与任何将要送入模型的上下文。本迭代若需访问私有仓库而使用 token，必须走配置管理并做脱敏。
- 默认禁止自动合并；本迭代不产生任何远端写副作用。
- 对第三方真实仓库执行代码属于高风险操作：请让该路径**显式开启**（默认关闭），并保证仅用于已验证的受控仓库。

### 7.4 可替换的抽象边界（为后续阶段预留）

即使本迭代用最简实现，也要把易变的部分隔离在接口之后，方便阶段二至阶段四替换：

- **任务存储**：定义 `TaskStore` 抽象 + 一个内存（或本地文件）实现。后续替换为 PostgreSQL 时不改动上层业务逻辑。
- **任务执行调度**：定义执行器抽象 + 一个进程内实现。后续替换为 Redis 队列时不改动 API 层。
- **沙箱执行**：定义 `SandboxExecutor` 抽象，所有子进程调用只允许经它发生。后续替换为 Docker 实现。
- **检查器**：定义统一的 checker 接口（输入工作区 → 输出问题记录与原始结果），新增检查器不需要改报告生成逻辑。

请在 `docs/architecture.md` 中画出模块边界与数据流，并标明每个抽象的可替换点。

### 7.5 代码质量

- 类型标注覆盖新增公共函数；模块职责单一。
- `ruff check .` 与 `ruff format --check .` 必须通过。
- 不使用通配符导入；不吞异常（禁止裸 `except: pass`）。

## 9. 验收标准（Definition of Done）

全部满足才算完成：

1. `python -m pytest` 全绿，且包含一条端到端测试：对受控 fixture 仓库 `POST /api/tasks` → 轮询 `GET /api/tasks/{id}` 直到 `succeeded` → `GET /api/tasks/{id}/report` 返回符合 §6 契约的结构化问题列表。
2. `ruff check .` 与 `ruff format --check .` 通过。
3. 服务可本地启动，`POST /api/tasks` 对 fixture 仓库能真实产出报告（提供可复制的命令与输出摘要）。
4. 仓库克隆在无网络时会**优雅失败**并给出明确 `failure_reason`，任务状态正确落到 `failed`，不挂死、不误报成功。
5. 基线 commit 被固定并记录在任务中，报告中能看到对应 commit。
6. 取消接口对运行中任务生效，状态落到 `cancelled`。
7. 无 `shell=True`；所有子进程有超时与输出上限；日志与报告中不含任何凭据。
8. 报告能正确区分「工具直接检测的问题」与「未验证的潜在问题」，且当前迭代不产生未经验证的问题被标记为已确认缺陷。
9. 文档更新到位：README 运行步骤、`docs/architecture.md` 模块边界与可替换点、`docs/open-questions.md` 记录所有歧义与假设。
